# Server development guide

## Назначение

Каталог `server` содержит backend приложения Journal: HTTP API,
бизнес-логику, предметную модель и работу с PostgreSQL.

Продуктовые требования находятся в `../docs/requires.md`. Общие правила
репозитория находятся в `../AGENTS.md`.

## Технологический стек

- Go
- Fiber
- OpenAPI
- Swagger UI
- PostgreSQL
- pgx
- Goose
- slog
- Make

Не заменять основные компоненты стека без отдельного архитектурного решения.

## Инструменты разработки

Инструменты проекта устанавливаются локально в `server/bin` командой:

```text
make deps
```

Версии инструментов фиксируются в `Makefile`. Не требовать от разработчика
ручной глобальной установки Goose и не использовать `@latest` в воспроизводимой
сборке. Каталог `server/bin` не добавляется в Git.

Миграции создаются только через команду:

```text
make migration-create name=short_migration_name
```

Не создавать новый файл миграции вручную. После создания Goose разрешено
редактировать SQL-содержимое сгенерированного файла.

## Архитектура

Сервер строится в соответствии с принципами DDD и разделяется на четыре слоя:

1. `api`
2. `service`
3. `domain`
4. `repository`

Направление вызовов:

```text
api -> service -> domain
          |
          v
      repository interface
          ^
          |
repository/postgres
```

Внешние слои могут зависеть от внутренних. Предметная область не должна
зависеть от Fiber, pgx, PostgreSQL, OpenAPI или деталей HTTP.

### api

Слой `api` отвечает только за HTTP:

- принимает и разбирает запрос;
- проверяет синтаксическую валидность HTTP-параметров;
- получает идентификатор и роль текущего пользователя;
- преобразует request в параметры вызова сервиса;
- вызывает один или несколько методов `service`;
- преобразует результат или ошибку в HTTP response;
- не содержит бизнес-правил;
- не обращается напрямую к базе данных или репозиториям.

Каждая ручка имеет собственные типы request и response. Не использовать одну
общую транспортную структуру для разных операций только из-за совпадения полей.
Имена должны отражать операцию, например:

```go
type CreateLessonRequest struct {
    SubjectID  string `json:"subjectId"`
    Date       string `json:"date"`
    Topic      string `json:"topic"`
    Homework   string `json:"homework"`
}

type CreateLessonResponse struct {
    ID string `json:"id"`
}
```

Transport-модели API не передаются в `domain` и `repository`. Handler явно
преобразует их в команды, запросы или значения слоя `service`.

### service

Слой `service` реализует сценарии использования приложения:

- координирует предметные операции;
- проверяет права доступа на уровне сценария;
- управляет границами транзакций;
- вызывает доменные методы;
- работает с репозиториями через интерфейсы;
- не зависит от Fiber и HTTP request/response;
- не содержит SQL.

Один публичный метод сервиса должен представлять понятный пользовательский
сценарий, например `CreateLesson`, `GradeStudent` или `GetChildJournal`.

### domain

Слой `domain` содержит предметную модель:

- сущности;
- value objects;
- предметные правила и инварианты;
- доменные ошибки;
- доменные сервисы, когда правило не принадлежит одной сущности.

Доменный код должен использовать стандартную библиотеку Go и минимальное
количество независимых библиотек. Он не должен импортировать Fiber, pgx,
OpenAPI-код, SQL-драйверы или пакеты слоя `api`.

Инварианты проверяются при создании и изменении доменных объектов. Нельзя
создавать заведомо некорректную сущность, а затем ожидать, что её исправит API.

### repository

Слой `repository` отвечает за сохранение и получение данных:

- интерфейсы описывают операции, необходимые сервисным сценариям;
- PostgreSQL-реализации используют `pgx`;
- SQL и преобразование строк базы данных находятся только в реализации
  репозитория;
- репозиторий возвращает доменные сущности или специально определённые модели
  чтения, а не типы `pgx.Row`;
- репозиторий не содержит HTTP-логики;
- репозиторий не принимает решений о правах пользователя.

Не создавать универсальный repository с методами CRUD для всех сущностей.
Интерфейсы должны отражать язык и реальные потребности предметной области.

## Рекомендуемая структура каталогов

```text
server/
  cmd/
    api/
      main.go
  api/
    openapi.yml
  internal/
    api/
      generated/
      handlers/
      middleware/
    service/
    domain/
    repository/
      postgres/
  migrations/
  Makefile
  go.mod
  go.sum
```

Каталоги внутри слоёв группируются по предметным областям, когда объём кода
этого требует. Не создавать пакет на каждый файл и не складывать весь слой
в один большой файл.

## OpenAPI и HTTP-контракт

Файл `api/openapi.yml` является основным контрактом HTTP API.

- Сначала изменить OpenAPI-контракт, затем выполнить кодогенерацию и написать
  реализацию.
- Все публичные endpoint, параметры, request body, response body и ошибки
  должны быть описаны в `openapi.yml`.
- Для каждой операции задавать уникальный `operationId`.
- Request и response каждой операции должны иметь отдельные именованные схемы.
- Общие простые схемы, такие как идентификатор или стандартная ошибка, можно
  переиспользовать через `$ref`.
- Не редактировать сгенерированный код вручную.
- Результат кодогенерации должен быть воспроизводимым и добавляться в Git,
  если это установлено структурой проекта.
- Swagger UI должен использовать актуальный `api/openapi.yml`.

Кодогенерация запускается через Make:

```text
make generate
```

Команда должна генерировать серверные интерфейсы и транспортные модели,
не изменяя вручную написанный код. После изменения `openapi.yml` необходимо
выполнить `make generate` и проверить отсутствие незакоммиченного расхождения
после повторной генерации.

## Ошибки API

API возвращает единый формат ошибки, определённый в OpenAPI, например:

```json
{
  "code": "lesson_not_found",
  "message": "Lesson not found"
}
```

- `code` является стабильным машинным кодом.
- `message` предназначен для человека и не раскрывает внутренние детали.
- Доменные и сервисные ошибки преобразуются в HTTP-статусы в слое `api`.
- Не возвращать клиенту SQL, stack trace, внутренние имена таблиц или секреты.

## PostgreSQL и pgx

- Использовать `pgx` для подключения к PostgreSQL и выполнения запросов.
- Все запросы должны принимать `context.Context`.
- Использовать параметры SQL вместо конкатенации пользовательских значений.
- Явно обрабатывать отсутствие строк и нарушения ограничений.
- Транзакции начинать на уровне сценария приложения, а не скрывать внутри
  несвязанных вызовов репозитория.
- Ограничения базы данных должны поддерживать ключевые инварианты: внешние
  ключи, уникальность и обязательность значений.
- Не использовать удаление каскадом без осознанного решения о жизненном цикле
  данных.

## Миграции Goose

Миграции находятся в каталоге `migrations` и выполняются через Goose.

- Каждое изменение схемы оформляется новой миграцией.
- Уже применённые миграции не редактируются.
- Миграция содержит секции `Up` и `Down`, если откат безопасен и возможен.
- Опасные или необратимые операции должны быть явно отмечены в миграции.
- Имена миграций должны кратко описывать изменение.
- Порядок применения миграций должен быть воспроизводимым.

Основные команды предоставляются через Make:

```text
make migration-create name=create_lessons
make migrate-up
make migrate-down
make migrate-status
```

Пароли и строка подключения передаются через переменные окружения и не
записываются в Makefile или миграции.

## Логирование

Для логирования использовать стандартный пакет `log/slog`.

- Логи должны быть структурированными.
- Передавать logger через зависимости, не использовать неуправляемые глобальные
  логгеры в бизнес-коде.
- Добавлять к запросам correlation/request ID.
- Логировать метод, путь, статус и длительность HTTP-запроса.
- Не записывать в логи пароли, токены, cookies и чувствительные данные детей
  или родителей.
- Ожидаемые ошибки пользователя не логировать как системные сбои.
- Не дублировать одну ошибку на каждом слое; логировать её там, где имеется
  достаточный контекст и принимается решение о результате операции.

## Зависимости и конструирование приложения

- Зависимости создаются в `cmd/api/main.go` или отдельном composition root.
- Использовать явное внедрение зависимостей через конструкторы.
- Избегать package-level mutable state и service locator.
- Конфигурация читается при запуске, валидируется и передаётся компонентам.
- Завершать HTTP-сервер и пул PostgreSQL корректно при остановке приложения.

## Тестирование

- `domain`: unit-тесты предметных правил и граничных условий.
- `service`: тесты сценариев, прав доступа и взаимодействия с repository
  interfaces.
- `api`: тесты HTTP-контракта, статусов, сериализации и валидации.
- `repository/postgres`: интеграционные тесты запросов и миграций с PostgreSQL.
- Сгенерированный код напрямую не тестировать.

Перед завершением серверного изменения выполнить доступные проверки через Make:

```text
make test
make lint
make generate
make build
```

Команды Make должны быть пригодны для локального запуска и CI.
