# Journal development guide

## Структура проекта

Проект состоит из двух основных частей:

- `client` — клиентское веб-приложение на React и TypeScript;
- `server` — серверное приложение и REST API на Go.

PostgreSQL используется как основная база данных. Локальное окружение
запускается через Docker Compose.

Продуктовые требования и границы первой версии описаны в
`docs/requires.md`. Перед изменением бизнес-логики необходимо проверить
этот документ.

## Ответственность частей системы

### Client

- Отображает интерфейс администратора, учителя и родителя.
- Получает и изменяет данные только через API сервера.
- Не содержит правил, от которых зависит безопасность данных.
- Не использует скрытие элементов интерфейса как способ ограничения доступа.
- Проверяет пользовательский ввод для удобства, но не заменяет серверную валидацию.

### Server

- Владеет бизнес-логикой приложения.
- Проверяет аутентификацию и права доступа для каждого защищённого запроса.
- Валидирует входные данные независимо от клиента.
- Работает с PostgreSQL и управляет транзакциями.
- Не раскрывает пользователю данные других семей или недоступных ему классов.
- Возвращает клиенту единообразные и понятные ошибки API.

## Архитектурные правила

- Клиент и сервер развиваются как отдельные приложения в одном репозитории.
- Сервер состоит из четырёх слоёв: `api`, `service`, `domain`, `repository`.
  `api` отвечает только за HTTP; `service` открывает и завершает транзакцию;
  `domain` принимает транзакцию и репозиторий и проверяет доменные правила;
  `repository` выполняет только операции над таблицами. Зависимость `domain`
  от абстракций транзакции и репозитория является осознанным отступлением от
  классического DDD этого проекта.
- Контракт API должен быть явным и версионируемым.
- Изменения структуры базы данных выполняются через миграции.
- Нельзя создавать отдельные таблицы базы данных для каждого класса,
  предмета или учебного года.
- Данные разных учебных лет хранятся в одной модели с явной связью
  с учебным годом.
- Основные сущности используют стабильные идентификаторы.
- Пароли никогда не хранятся в открытом виде.
- Секреты и production-конфигурация не добавляются в Git.
- Новые зависимости и инфраструктура добавляются только при практической необходимости.
- Существенные архитектурные решения документируются в каталоге `docs/`.

## Правила разработки

- Перед изменениями изучать существующую структуру и соглашения проекта.
- Делать небольшие завершённые изменения.
- Не смешивать несвязанные изменения в одной задаче.
- Не изменять публичный контракт API без обновления клиента и документации.
- Для бизнес-правил, авторизации и контроля доступа писать тесты.
- Для компонентов клиента тестировать важные пользовательские сценарии.
- После изменения запускать относящиеся к нему тесты, линтеры и сборку.
- Сохранять обратную совместимость миграций, если это возможно.
- Если требование влияет на модель данных, безопасность или пользовательский
  процесс и допускает существенно разные решения, сначала уточнить его.

## Организация Go-файлов сервера

- В пакете `api` тип HTTP-сервера или обработчика и используемые им интерфейсы
  размещаются в `server.go`.
- Конструкторы зависимостей API размещаются в `service.go`, регистрация
  маршрутов — в `route.go`, общие HTTP-ошибки — в `errors.go`.
- Каждая HTTP-ручка размещается в отдельном файле, названном по операции,
  например `login.go`. Тесты этой ручки размещаются в одноимённом файле с
  суффиксом `_test`, например `login_test.go`.
- В пакете `service` тип сервиса и его конструктор размещаются в `service.go`.
  Каждая операция сервиса размещается в отдельном файле, названном по операции,
  с тестами в соответствующем файле `<operation>_test.go`.
- В пакете `domain` тип домена, его зависимости и фабрика размещаются в
  `domain.go`. Каждая доменная операция размещается в отдельном файле и
  принимает отдельную структуру `Request`, возвращая отдельную структуру
  `Response`; тесты операции размещаются в соответствующем файле
  `<operation>_test.go`.`r`n- В пакете `repository` общие ошибки размещаются в `errors.go`, интерфейсы
  транзакций и их менеджера — в `transaction.go`, интерфейсы репозиториев — в
  `repository.go`.
- Каждая структура данных репозитория размещается в отдельном файле, названном
  по сущности, например `user.go` или `session.go`.
- В реализациях репозитория тип репозитория и его конструктор размещаются в
  `repository.go`, а менеджер транзакций и вспомогательный код транзакций — в
  `transaction.go`. Операции над конкретной областью данных группируются в
  отдельном файле этой области, например `auth.go`.

## Работа с ревью

Пользователь выполняет ревью изменений и оставляет комментарии с тегом
`codex: замечания`.

- Каждый комментарий с тегом `codex: замечания` является заданием на внесение
  изменений.
- Искать и обрабатывать комментарии `codex: замечания` только в файлах,
  изменённых относительно текущего состояния Git. Не сканировать для этого весь
  проект и не изменять незатронутые файлы.
- Перед исправлением необходимо прочитать комментарий и изучить связанный с ним
  код и контекст.
- Нужно устранить причину замечания, а не только изменить указанную строку.
- Все замечания с этим тегом должны быть обработаны, если они не противоречат
  друг другу или актуальным требованиям проекта.
- После исправлений необходимо запустить проверки, относящиеся к изменённому
  коду.
- В результате работы нужно кратко перечислить исправленные замечания и указать
  выполненные проверки.
- Если замечание невозможно выполнить или оно требует изменения согласованных
  требований, нужно объяснить причину и запросить решение пользователя.
